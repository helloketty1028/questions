## 答题逻辑（中文，3–5 步）
1. 诚实：MongoDB 经验来自早期平台（Sohu、Baidu、AI Park）。
2. 给判断标准：结构多变的文档 → MongoDB；需要对平的账、多实体事务 → 关系库。
3. 设计要点：embed 还是 reference、索引顺序、write concern、事务慎用。
4. 混合架构：关系库作为 system of record，CDC 同步到 MongoDB 支撑查询。

## 30s
> My MongoDB experience is from earlier platforms — Sohu's CMS, Baidu's order system and AI Park — so I'd refresh on the latest versions. I'd choose MongoDB when the data is naturally a document with varying structure — like a trade with nested lifecycle events and product-specific fields — and a relational database when you need strong multi-entity transactions and joins, like positions or ledgers that must balance.

## ATL — 60s
> My MongoDB work is from earlier platforms — Sohu's CMS, Baidu's order system and AI Park — so I'd be honest that I'd refresh on the latest versions. The design judgement is what matters. I'd choose it when the data is naturally a document with varying structure: in post-trade, different products carry different fields and nested lifecycle events, and a document model avoids dozens of tables or one huge wide table. I'd keep a relational store for data that must balance, like positions and ledgers. Design points: embed versus reference by read pattern; indexes that follow the query — equality, then sort, then range; write concern majority for financial data; multi-document transactions only when really needed. A common pattern is relational as the system of record, with CDC into MongoDB for high-volume reads.

## 追问与应对
- **Q**：How do you design indexes? / **A**：ESR 规则：equality → sort → range；用 explain() 验证；不要给每个字段都建索引。
- **Q**：Transactions? / **A**：4.0 起支持多文档事务，但代价高——优先用单文档原子性来设计数据模型。
