## 答题逻辑（中文，3–5 步）
1. Python：GIL → 线程适合 I/O 密集，进程（multiprocessing）适合 CPU 密集；asyncio 适合大量 I/O。
2. Java：ExecutorService、synchronized / ReentrantLock、Semaphore、CountDownLatch / CyclicBarrier、ConcurrentHashMap、CompletableFuture。
3. Java 21 虚拟线程：适合大量阻塞 I/O；不要池化；注意 pinning。
4. 诚实：生产中的并发经验在 Java，不在 Python。

## 30s
> In Python, the GIL means only one thread runs Python bytecode at a time, so threads suit I/O-bound work and processes suit CPU-bound work; asyncio suits large amounts of I/O. In Java, real threads run in parallel, so I use executors, locks, semaphores to cap concurrent access, latches and barriers to coordinate, and concurrent collections. Since Java 21, virtual threads make blocking I/O cheap at high concurrency. My production concurrency work has been in Java.

## ATL — 60s
> Python first: the GIL lets only one thread execute Python bytecode at a time, so threads help with I/O-bound work like file or network calls, while CPU-bound work needs multiprocessing — separate processes, separate memory, communicating through queues. asyncio is the third option for many concurrent I/O tasks. Java is different: threads run truly in parallel, so correctness needs coordination. I use ExecutorService rather than raw threads; synchronized or ReentrantLock for mutual exclusion; Semaphore to cap concurrent access to a scarce resource, like a downstream API; CountDownLatch or CyclicBarrier to coordinate phases; and ConcurrentHashMap and CompletableFuture. Java 21 virtual threads make thread-per-request cheap for blocking I/O — but don't pool them, and watch for pinning inside synchronized blocks. My production concurrency work is in Java.
