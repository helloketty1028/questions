## 答题逻辑（中文，3–5 步）
1. 代码：Bitbucket + 分支策略 + PR review（加上 AI review）。
2. 构建与测试：Jenkins、JUnit、SonarQube 质量门禁、自动化回归和渗透测试。
3. 制品与部署：Aldon 管理各环境的部署包。
4. 发布治理：SIT / UAT sign-off、CRQ / CAB；上线后用 Splunk 监控。
5. 收益：快速、可重复、可审计。

## 30s
> Code lives in Bitbucket, with a branching strategy and pull-request review. Every change goes through Jenkins: build, JUnit tests, the SonarQube quality gate, automated regression and penetration testing. Aldon manages the deployable packages across environments. Releases need SIT and UAT sign-off, and I take each production change through CAB. The benefit is fast, repeatable releases with an audit trail — exactly what a regulated bank needs.

## ATL — 60s
> Stage by stage. Source: Bitbucket with a branching strategy; every pull request gets a human review, and since May 2026 an AI review as well — a headless Claude Code agent comments on security, performance, correctness and maintainability. Build and test: Jenkins builds the artefact and runs JUnit, then the SonarQube quality gate, automated regression and penetration testing — a failure stops the pipeline. Release management: Aldon manages the deployable packages and their promotion across environments, so we always know exactly which build is where. Then SIT and UAT, the change request through CAB, and after go-live, Splunk transaction monitoring and alerting. The benefits: fast feedback, repeatable deployments, and an audit trail for every change.

## TPM — 60s
> For me the pipeline is the governance backbone. Every change carries its own evidence: tests passed, quality gate passed, security tests passed, and which build went where. That's what lets me require SIT and UAT sign-off on every release and take each production change through CAB without slowing the team down — the evidence is already there. I track delivery health on top: deployment frequency, MTTR, incident trend and change-failure rate.
