## 答题逻辑（中文，3–5 步）
1. 先问意图：分担工作 → 同一个 consumer group；每个都要全量 → 不同的 group。
2. 顺序只在分区内保证 → 按业务 ID 做 key。
3. 关键配置：手动提交、max.poll.*、auto.offset.reset、read_committed；producer 端 acks=all + idempotence。
4. at-least-once → consumer 必须幂等。
5. 你的 Kafka 生产经验来自 VV、AI Park（不是 UOB hub）。

## 30s
> Within one consumer group, each partition goes to exactly one consumer. So if the two services share the work, they join the same group; if each needs every message, they use different groups. Ordering only holds within a partition, so I key by business ID. And Kafka gives at-least-once delivery, so consumers must be idempotent, and commit offsets only after processing succeeds.

## ATL — 60s
> First, the intent. If the two services share the work, they're in the same consumer group, and each partition goes to one consumer — so parallelism is capped by the partition count. If each service needs every message, they're in different groups with independent offsets. Ordering is only per partition, so I key by business ID, like a trade or payment ID. Configs I always check: auto-commit off, committing only after processing succeeds; max.poll.records and max.poll.interval.ms, because slow processing gets a consumer kicked out and triggers a rebalance; auto.offset.reset for new groups; read_committed if producers use transactions. On the producer, acks=all with idempotence enabled. Even then it's at-least-once, so consumers must be idempotent. I've run Kafka in production for asynchronous flows at VV Technology and AI Park.

## 追问与应对
- **Q**：A consumer crashes mid-batch? / **A**：从上次提交的 offset 重投 → 会重复 → 靠幂等（处理过的 ID + 唯一约束）。
- **Q**：Poison message? / **A**：有限次重试 → 重试 topic → DLQ，加告警，人工处理。
- **Q**：How many partitions? / **A**：按目标吞吐 ÷ 单 consumer 吞吐估算，留余量；分区只能加不能减，而且加分区会改变 key 的映射。
