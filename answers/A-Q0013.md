## 答题逻辑（中文，3–5 步）
1. 六个维度的就绪检查：范围、质量、技术、运营、风险、治理。
2. 每个维度说一句"由什么证据证明"。
3. 用一个真实的例子收尾：ISO 20022 切换门禁（PA-01.1）。

## 30s
> I check readiness in six areas: scope is frozen and dependencies confirmed; quality — SIT, UAT, regression and security testing done, critical defects closed; technical — package, config, database scripts and pipeline verified; operational — runbook, owners, window and monitoring in place; risk — rollback triggers and plan clear; and governance — all approvals in. If any one is red, the release doesn't go.

## ATL — 60s
> For me the technical evidence matters most. The pipeline enforces quality gates — unit tests, SonarQube, automated regression and penetration testing — so by the time we talk about go-live, the basics are proven. Then I check the deployment package, configuration and database scripts; database changes get special attention because they're often the hardest part to reverse, and they're part of what I present at CAB. I make sure monitoring is ready: we use Splunk-based transaction monitoring and alerting, so we know quickly if something goes wrong after cutover. And the rollback plan has to name a clear trigger, not just exist.

## TPM — 60s
> I use six readiness checks. **Scope**: release scope, versions and dependencies confirmed, no uncontrolled late changes. **Quality**: SIT, UAT, regression and security testing completed, critical defects closed — I require SIT and UAT sign-off for every release. **Technical**: environments, deployment package, configuration, database scripts and the pipeline verified. **Operational**: cutover runbook, owners, time window and monitoring arranged. **Risk**: dependencies, rollback triggers and rollback plan clear. **Governance**: approvals in place — I prepare the change request and present it at CAB myself. On the ISO 20022 migration, those gates are what let us cut over with no service interruption.

## SM — 60s
> I make readiness a go / no-go decision with named owners and an evidence trail, not a feeling. Six areas — scope, quality, technical, operational, risk and governance — each with an accountable owner. I present every production release at CAB myself, so I see the whole picture before it goes. The point isn't bureaucracy: when the evidence is complete, the decision is fast. That discipline is why our ISO 20022 cutover had no service interruption, and why we can keep shipping every two to three months.

## 追问与应对
- **Q**：Did you have a formal performance test? / **A**：见待确认 SB-03——**不要说有**。
- **Q**：What triggers a rollback? / **A**：讲原则：上线后关键交易失败、监控指标越过阈值。不编具体数值。
- **Q**：Do you have a QA team? / **A**："Yes — internal testers, then dedicated SIT and UAT teams; every release needs SIT and UAT sign-off."（PA-03.1；QA 是 PA-03 §9 的干系人）
- **Q**：How do you test and deploy to production? / **A**：pipeline 门禁（PA-03.2）→ SIT / UAT sign-off → CRQ 和 CAB（PA-03.5）→ 上线与 Splunk 监控（PA-02.2）。
