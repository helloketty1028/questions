## 答题逻辑（中文，3–5 步）
1. 思路：分层控制，任何一层都不需要完美。
2. 发布前：feature flag，代码可以关着上线。
3. 发布中：blue-green / canary / active-passive，回滚触发条件要明确。
4. 高风险逻辑：shadow / parallel run，对比新旧输出。
5. 真实例子：ISO 20022 的分阶段共存。

## 30s
> Layers, so no single control has to be perfect. Before release, feature flags, so code can go out switched off. During release, blue-green or canary with a clear rollback trigger. For high-risk changes, a parallel or shadow run, comparing the new logic with the old on real input before switching. On our ISO 20022 migration, that's what a phased coexistence gave us: old and new running side by side, with a way back at every step.

## ATL — 60s
> When UAT can't reproduce production — data, reference data or connected systems — I reduce the blast radius instead of pretending to test everything. Ship dark behind a feature flag, then enable it for a small slice: one instance, one user group or one corridor. Use blue-green or active-passive: deploy to the passive side, verify, then switch, with a rollback plan that names a clear trigger. For high-risk logic, run it in shadow mode on real input and compare the output with the existing path before it takes effect. And watch closely: Splunk-based transaction monitoring and alerting tell us quickly if behaviour drifts. That's the thinking behind our ISO 20022 phased coexistence.

## TPM — 60s
> I make it a release-plan question, not just a test question. Every production release on my platforms needs SIT and UAT sign-off, and I present the change at CAB with the go-live plan, risk controls, rollback plan, impact assessment and database changes. For whatever UAT can't cover, the plan has to say how we limit exposure on day one — a phased rollout, a feature flag or a parallel run — who is watching, and what triggers a rollback. On the ISO 20022 migration we ran MT and MX in coexistence with readiness gates rather than a big-bang cutover, and retired coexistence in August 2026 with no service interruption.
